# One daemon and data store per DSH home

A DeepSeek Harness home that wants its own Issues gets its own `shared-context` daemon, config, SQLite database, and attachment/backup directories under `$DSH_HOME/shared-context`; a home with no such directory keeps using the shared legacy instance on `127.0.0.1:4319`, which is how the existing `empresa` store stays untouched. Row-level profile filtering in one database would keep one process and one backup, but every repository query, full-text search, SSE replay, and MCP tool would have to enforce the filter, and one missed predicate would leak company Issues into the personal board. Process/store isolation makes the boundary physical and gives each home its own token and backup schedule, at the cost of one daemon and one backup schedule per active home and a DSH restart when a home's endpoint changes; this is separation of local state, not a security boundary, because both daemons run as the same user, who can read both configs and databases. ADR-0001 and ADR-0005 still describe the shape within each store.
